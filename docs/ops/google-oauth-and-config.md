|---|---|---|
| `NEXT_PUBLIC_ACCOUNTS` | the literal `on` | **Production only.** *Inlined at build time*: changing it needs a redeploy. Preview and Development stay **unset** (accounts off) |

## 4. How the credentials stay server-side (verified now, re-verified in 7B)
* **Repository:** `.env*` is gitignored (only `.env.example`, which contains names and comments, is tracked); CI runs gitleaks on every push; `grep` of the repo shows the project ref (not a secret) only in docs.
* **Browser bundles:** the only public variable is `NEXT_PUBLIC_ACCOUNTS`. An architecture test (`boundaries.test.ts`) fails if any `NEXT_PUBLIC_*` name contains SUPABASE/KEY/SECRET/PEPPER/TOKEN/SERVICE, if a client component imports a Supabase package or server auth code, or if a secret variable is read outside `config.ts`. **Checked now:** a scan of the built client bundles (`.next/static`, `.next-accounts/static`) finds no service-role, pepper, flow-secret or cron-secret names, no JWT-shaped strings and no `supabase.co` hostname. 7B repeats this scan on the production build artefact before accounts are switched on.
* **Logs:** the account logger accepts only fixed outcome words (tested); no request body, header, cookie or URL query is logged by the app. Vercel's own request logs record path and status. Never paste a key into a ticket, chat, terminal recording or screenshot.
* **Rotation plan:** if any secret is exposed, rotate in this order: service-role key (Supabase → API keys), `AUTH_FLOW_SECRET` (invalidates in-flight sign-ins only), `CRON_SECRET`, then Google client secret. Rotating `INVITE_CODE_PEPPER` invalidates every unused invitation and breaks ledger replay for deletions made under the old value: generate new invitations afterwards and keep the old pepper until the ledger's 35 days have passed.
* **Who can read them:** limit Vercel team members and Supabase org members to the two owners; no secrets in GitHub Actions for production (CI uses the local stack only).
